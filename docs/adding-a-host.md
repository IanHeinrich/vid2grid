# Adding a host

A host (or head) is whatever turns a video into collage sheets on one runtime:
the browser app, the Python library, the Node.js library. Every decision
about frames, layout, text and file names is core's, made once in the
[`RenderPlan`](render-plan.md). A host only does the four things core cannot do
without touching media, and proves it does them the same way as the others.

## What a host implements

1. **Probe.** Read the video's `VideoInfo`: `durationSeconds`, and `width` and
   `height` as displayed (rotation applied, and the sample aspect ratio applied
   through core's `displaySize`). In keyframe mode it also reads
   `keyframeTimestampsSeconds`, every keyframe's presentation time in seconds,
   ascending. That costs a full demux, so read it only when the request asks
   for keyframe sampling.
2. **Capture.** For each `plan.frames` entry, in order, decode the first frame
   whose presentation time, rounded to microseconds with
   `floor(t * 1e6 + 0.5) / 1e6`, is at or after `timestampSeconds`. Turn it
   clockwise by the container's display rotation, which is 0, 90, 180 or 270:
   ffmpeg reports it counter-clockwise, and core's
   `normalizeRotationClockwise` flips and rounds it. Then scale it to exactly
   `plan.cell`. `VideoInfo` does not carry the rotation, so the host keeps it
   from the probe. Several planned times can pick the same source frame.
   Return fewer images only when the stream ends first. A keyframe plan may
   decode keyframes alone. Hand images over as they are decoded rather than
   all at once: a JavaScript host's `capture` is an async iterable that
   yields them in plan order and decodes no further ahead than the pipeline
   pulls, and its optional `release` frees an image the pipeline pulled but
   will never encode.
3. **Run draw ops.** For each sheet, run `sheetDrawOps(plan, sheetIndex)` on a
   `plan.canvas`-sized surface, in order: a background `fillRect`, then per
   cell an `image` op and its `text` ops. Skip both for a cell with no captured
   image. Text is stroked, then filled, and a `top-right` anchor gives the
   text's right edge, which only the host's own font metrics can resolve.
4. **Encode JPEG.** Encode each sheet at `plan.jpegQuality` and name it
   `sheet.fileName`. A JavaScript host's `encode` takes one sheet, owns its
   images from the call on and frees them whatever the outcome. Its
   `concurrency` says how many sheets may encode at once, 1 when unset.

Transcription is optional. A host that offers it fills the
`TranscriptPort` in
[`pipeline/ports.ts`](../packages/core/src/pipeline/ports.ts) and writes the
cues inside each sheet's `transcript` window; one that does not just leaves
`transcript` out of the request. Core's
[`transcript/`](../packages/core/src/transcript/) does the rest:
`cuesFromSegments` turns a recogniser's segments into cues on the video's
timeline, `transcriptFiles(plan, renderedSheetCount, endSeconds, cues)` gives
each `.vtt` file's name and text, and `transcriptionFailedWarning` and
`noTranscriptionPortWarning` (`NO_TRANSCRIPTION_PORT` in TypeScript) are the
warnings to report instead of failing the run. All four are in the embed.

## Two ways to get the planner

**In a JavaScript runtime**, depend on `@vid2grid/core`. Implementing
`CollagePorts` and calling `generateCollages` gets the whole sequence,
including the keyframe fallback and progress. `streamCollages` runs the same
sequence but hands each sheet to an awaited `onSheet` in sheet order as soon
as it and every earlier sheet are encoded, and keeps none of them, so a host
that writes sheets to disk holds no more than the sheets in flight. A host
with a canvas-like 2D context can paint with `paintSheetFromPlan` instead of
its own draw-op loop.
`packages/browser` is the worked example, and `apps/node-library` (ffmpeg and
`@napi-rs/canvas`) is a headless one whose `tests/conformance.test.ts` checks
it against the draw-op and frame goldens. It runs core's planner directly, so
the render-plan goldens have nothing of its own to check. Its CLI, built from
`OPTION_SPECS`, is a separate app in `apps/node-cli`.

**In any other runtime with a JavaScript engine**, embed
`apps/python-library/src/vid2grid/_core.js` (generated by `npm run bundle`,
never edited).
Evaluate it once; it defines a global `vid2gridCore` whose one function,
`call(name, argsJson)`, takes a function name and a JSON array of positional
arguments and returns a JSON envelope: `{"ok": true, "value": ...}` or
`{"ok": false, "code": ..., "message": ...}`, with `code` one of
`invalid_request`, `no_audio`, `no_frames` and `internal`. The functions and
their argument shapes are listed in
[render-plan.md](render-plan.md#hosts-without-javascript). Leave an unset
optional field out of the JSON rather than sending `null`.
`apps/python-library` runs it in `mini-racer`; its `src/vid2grid/_core.py` is
the worked example.

## The per-sheet loop

```
info     = probe(video, keyframes = options.keyframeSampling)
request  = core.requestFromOptions(options, info, capabilities)
core.validateCollagePlanRequest(request)
decision = core.resolveKeyframeSampling(request, info, keyframeReadError)  # report decision.warning
plan     = core.buildRenderPlan(decision.request, info)
frames   = capture(video, plan)                       # lazy, cell-sized, at-or-after rule
for sheet in plan.sheets:
    images = take(frames, len(sheet.cells))
    if images is empty: break                         # the stream ended
    surface = new_surface(plan.canvas)
    for op in core.sheetDrawOps(plan, sheet.sheetIndex):
        if op.kind != "fillRect" and op.cellIndex >= len(images): continue
        draw(surface, op, images)
    write(encode_jpeg(surface, plan.jpegQuality), sheet.fileName)
```

Taking one sheet's images at a time keeps memory to a sheet, whatever the
video's length. The Python library does that. `generateCollages` and
`streamCollages`, which the browser and Node hosts run, do the same with
encodes in flight: they pull frames in plan order, start a sheet's encode as
soon as its cells are captured, and once `concurrency` encodes are running
they wait for the oldest to be delivered before pulling more. A JavaScript host
therefore holds at most about `concurrency + 1` sheets of frames. When the
capture ends early, the sheet it was part way through is encoded with its
missing cells empty. On any error they stop pulling, close the capture with
its iterator's `return()`, `release` every frame no encode took, let the
encodes in flight settle and rethrow the first error.

## Proving conformance

A canvas and Pillow rasterise the same text differently, so rendered JPEG
bytes are never compared across hosts. Conformance is checked on what is host
independent, with the goldens under [`fixtures/`](../fixtures/):

- **Plans.** Each `fixtures/render-plans/<case>.json` holds a `request`, an
  `info` and the `plan` core builds from them. A host that calls the planner
  through its own binding asserts it gets that plan back, as
  `apps/python-library/tests/test_planner.py` does.
- **Draw ops.** Each `fixtures/draw-ops/<case>.json` holds `sheets`, where
  `sheets[i]` is `sheetDrawOps(plan, i)` for the same case's plan. A host
  asserts its binding returns them, and tests its painter against them:
  position, size, text and order, not pixels.
- **Frame selection.** Each `fixtures/frames/<case>.json` names a `video` under
  `fixtures/videos/`, the `request` and probed `info`, the
  `sourceFrameSeconds` of the source frames from just before the first pick to
  the last, and per planned frame its `plannedSeconds` and the
  `decodedSeconds` of the source frame the capture rule picks. A host probes
  the video and compares against `info`, rebuilds the plan from `request` and
  `info`, captures, and compares the presentation time of each frame it picked
  (rounded to microseconds) with `decodedSeconds`. Its capture needs a way to
  report those times in tests. There are two videos: `tiny.mp4`, and
  `keyframes-20s.mp4`, whose keyframe every second makes a sparse plan reseek
  and gives keyframe mode many keyframes to choose from.

`npm run fixtures` writes the plan and draw-op goldens, and CI fails if they
drift. The frame goldens come from a real decode, so they are recorded by hand,
from `apps/python-library/`:

```
uv run python ../../scripts/recordFrameFixtures.py
```

The script reads `sourceFrameSeconds` from its own decode of every frame,
independent of any host's capture, applies the rule to get `decodedSeconds`,
and stops without writing if the Python library's capture picks differently.
That makes it a cross-check on that capture too. Rerun it after adding a case
or a video. `scripts/makeKeyframeVideo.py`, run the same way, writes
`keyframes-20s.mp4`. A planner change that moves the planned times fails
`packages/core/tests/frameFixtures.test.ts` until it is.

## Options for a CLI or tool

`OPTION_SPECS` in [`plan/options.ts`](../packages/core/src/plan/options.ts)
lists every option a CLI or tool can expose. Each has a `name` (the request
field, or `transcript` for the transcript scope), a kebab-case `flag`, a `type`
(`number`, `integer`, `boolean` or `enum`) and a one-line `help`. Where they
apply it also has a `default`, a `min` and `max` (both inclusive), an
`exclusiveMin` (strict, as JSON Schema names it), the `values` of an enum and
a `requires` naming the host capability it needs. The bounds mirror what
`validateCollagePlanRequest` enforces on the same field; whether an `integer`
is whole is checked only by `requestFromOptions`.

A host gets its options from `optionSpecsFor(capabilities)` (`optionSpecs`
through the embed, `option_specs(capabilities)` in Python) and converts the
values it parsed with `requestFromOptions(values, info, capabilities)`. That
fills in the defaults, ending at the video's duration when no end is given,
and returns a `CollagePlanRequest`. It rejects an unknown name, a value of the
wrong type and an enum value outside `values` as `invalid_request`. Only
`transcript` has a `requires`, `transcription`, so a host without
transcription passes no capabilities and never offers it.

The defaults are the web app's startup values, and the resolution comes from
the first model preset. `apps/web/tests/optionDefaults.test.ts` fails if its
form and the spec disagree. Build flags and usage text from the spec rather
than a table of your own.

## Checklist

A host is an executor library plus the entry points built on it, each its own
folder under `apps/`. Add the library first; a CLI or server on top of it is a
separate app that depends on it, as `apps/node-cli` does on `apps/node-library`
and `apps/python-cli` and `apps/mcp-server` do on `apps/python-library`.

- The library in `apps/<runtime>-library/`, with tests in
  `<app>/tests/<module>.test.ts` (or `tests/test_<module>.py`).
- Conformance tests over `fixtures/render-plans/`, `fixtures/draw-ops/` and
  `fixtures/frames/`.
- Each entry point in its own `apps/` folder, with flags and usage built from
  `OPTION_SPECS`.
- A JavaScript app added to the root `package.json` `workspaces`, which lists
  apps by name; an app in another language keeps its own toolchain and is
  checked from its own folder.
- A CI job in [`pages.yml`](../.github/workflows/pages.yml) that runs them.
  The `push` path filter already covers `apps/**`, `packages/**`,
  `fixtures/**` and `scripts/**`; extend it only for files outside those.
- A row per app in the "Ways to use vid2grid" table in the
  [README](../README.md).
- A row per folder in the package table in [CLAUDE.md](../CLAUDE.md), and a
  chunk per folder in
  [`.claude/rules/parallel-work.md`](../.claude/rules/parallel-work.md).
- Any deviation from the capture rule written down under "What an executor
  must do" in [render-plan.md](render-plan.md), as the browser's `<video>`
  fallback is.
